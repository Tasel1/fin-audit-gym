# Записка о дизайне среды Fin-Audit-Gym

> Симулятор финансового аудита и воспроизводимая RL-среда для дообучения и оценки ИИ-аудиторов.

---

## 1. Введение и концепция

Цель `Fin-Audit-Gym` — предоставить исследователям и разработчикам строго математическую, изолированную симуляционную среду (в стиле Gymnasium), имитирующую внутренний контур корпоративного финансового учета компании.

Среда решает ключевую проблему оценки ИИ в финтехе: **невозможность проверки причинно-следственных связей без утечки эталона (Zero Data Leakage)** и **защиту от взлома целевой функции (Specification Gaming)**.

---

## 2. Архитектура симулятора

Симулятор состоит из трех строго разделенных контуров:

```
┌────────────────────────────────────────────────────────┐
│             1. Генератор (Synthetic World Engine)      │
│  - Бухгалтерский контур двойной записи (Дебет = Кредит)│
│  - Детерминированный граф транзакций (Seed-reproducible)│
│  - Инжекторы 4 классов аномалий и 2 комбинаций         │
│  - Дистракторы (легитимные шумы: сплиты, подписки)     │
└───────────┬────────────────────────────────┬───────────┘
            │                                │
 (Открытые файлы компании)          (Закрытые файлы оценщика)
            │                                │
            ▼                                ▼
┌────────────────────────┐      ┌────────────────────────┐
│  2. Агентская среда    │      │  3. Оценщик (Evaluator)│
│  - reset() / step()    │      │  - Kuhn-Munkres 1-to-1 │
│  - Ограниченный API    │      │  - Допуски сумм        │
│  - Лимит 100 шагов     │      │  - Проверка улик       │
│  - Без доступа к FS/OS │      │  - Расчет F1 и Reward  │
└───────────┬────────────┘      └────────────▲───────────┘
            │                                │
            └────── submit(findings) ────────┘
```

## 3. Генерация данных и бухгалтерская строгость

1. **Двойная запись (Double-Entry Bookkeeping)**:
   - До внесения аномалий генератор создает идеальный мир, в котором сумма дебетовых проводок строго равна сумме кредитовых: $\sum \text{Debit} = \sum \text{Credit}$.
   - Все денежные суммы выражаются в целочисленных минимальных единицах валюты (`minor_units`, например, центы или тиыны), исключая ошибки округления чисел с плавающей точкой.
2. **Инъекция ошибок и Provenance**:
   - При внесении аномалии генератор изменяет проводку или инвойс и одновременно регистрирует причинную связь в `provenance.json` (какой исходный факт был изменен, почему и на какую дельту).
   - Эталон `truth.json` содержит не случайные подозрительные строки, а минимально достаточные наборы доступных агенту доказательств (`evidence_ids`).

## 4. Классификация ошибок и сценарии взаимодействия

В соответствии с международными стандартами аудита (ISA 500 / IFRS / GAAP):
1. **Дубли счетов (`duplicate_invoice`)**: повторное выставление или двойное отражение одного обязательства в главной книге.
2. **Нераспределенный платеж (`unallocated_payment`)**: платеж без привязки к инвойсу или частичная оплата с необоснованным зависшим сальдо.
3. **FX-ошибка конвертации (`fx_mismatch`)**: применение курса валюты не на дату операции или арифметическая ошибка пересчета.
4. **Нарушение отчетного периода (`period_cutoff`)**: операция, совершенная за пределами отчетного периода, но проведенная текущей датой (или наоборот).

**Комбинированные сценарии**:
- *Сценарий 1*: Частичный платеж в иностранной валюте на стыке отчетных периодов (FX + Unallocated + Cutoff).
- *Сценарий 2*: Дубликат инвойса с частичным кросс-валютным возвратом, проведенным со сдвигом периода.

**Правдоподобные отвлекающие факторы (Innocent Look-Alikes)**:
- Легитимные сплит-платежи (два платежа закрывают один счет).
- Законные повторяющиеся платежи одинакового размера (ежемесячная аренда, подписка).
- Возвраты средств по кредитным нотам.

## 5. Защита от Specification Gaming (Анализ по DeepMind)

В соответствии с исследованиями *DeepMind (Krakovna et al., 2020)*, агенты пытаются хакнуть метрики следующими путями:

| Уязвимость | Как пытается хакнуть агент | Решение в Fin-Audit-Gym |
|---|---|---|
| **Reward Shaping Loophole** | Ходить по кругу и бесконечно читать записи, если за это дают награду. | Награда за шаги исследования **строго равна 0**. Награда только терминальная. |
| **Spam All Attack** | Отправить 30 случайных обвинений в надежде угадать хотя бы одну ошибку. | Биективный матчинг Kuhn-Munkres: каждое ложное обвинение становится FP, обрушивая Precision и F1 до 0 (Reward $\to -1.0$). |
| **Duplicate Claim Exploit** | Отправить одну верную находку 10 раз, чтобы завысить счетчик TP. | Венгерский алгоритм накладывает ограничение 1-в-1: первая находка дает TP, остальные 9 становятся FP. |
| **Clean Book Exploit** | Попытка найти несуществующие ошибки на чистых данных. | На чистых книгах пустое представление дает $F_1 = 1.0$ (максимальная награда), а любое ложное обвинение дает $F_1 = 0.0$ (штраф $-1.0$). |
| **Reward Tampering / Memory Leak** | Прочитать приватные поля класса среды или память оценщика. | Оценщик полностью отделен от пространства наблюдений агента; закрытые файлы недоступны через интроспекцию. |

---

## 6. Функция награды

Терминальная награда вычисляется по формуле:
$$R = \text{clip}\left(2 \cdot F_1 - 1 - 0.002 \cdot \text{inspection\_steps},\ -1,\ 1\right)$$

- При идеальном аудите ($F_1 = 1.0$) за 10 шагов: $R = 2(1) - 1 - 0.02 = 0.98$.
- При молчании на чистых книгах ($F_1 = 1.0$) за 5 шагов: $R = 2(1) - 1 - 0.01 = 0.99$.
- При спам-атаке ($F_1 = 0.0$): $R = -1.0$.
- При пропуске всех ошибок ($F_1 = 0.0$): $R = -1.0$.

---

## 7. Воспроизводимость и инвариантность

Среда гарантирует полную детерминированность:
- Одинаковая тройка `(seed, config, version)` дает идентичные записи, переходы и награды байт-в-байт.
- Перемешивание строк в `ledger.csv` и переименование идентификаторов (изоморфизм графа) не изменяет способность базовой политики Oracle получить максимальную награду.
